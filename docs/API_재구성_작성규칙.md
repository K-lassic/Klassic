## 1. API 코드 작성 규칙 (FastAPI · model-api 기준)

### 1-1. 요청 처리 4요소 (M12-A)
1. **입력 검증** — 요청 형태는 Pydantic 모델로 검증한다. 필드 누락·자료형 오류는 `422` 로 응답한다.
2. **리소스 로딩** — 모델·사운드폰트 같은 무거운 자원은 **시작 시점에 로딩**하고, 그 완료를 준비 상태의 기준으로 삼는다.
3. **처리** — 응답에 결과와 함께 **버전 정보**(서비스/모델 버전)를 포함할 수 있게 설계한다.
4. **오류 응답** — 내부 오류는 정직한 코드(`500`)와 메시지로 응답한다. 애매하게 버티지 말고 **진단 가능한 실패**를 택한다. (M7-B)

### 1-2. 경로·설정은 환경변수로 (M12-A, M10-D)
- 파일 경로(모델, 음원, 엔진 위치 등)는 하드코딩하지 않고 환경변수로 주입한다. 예: `MODEL_PATH`, `ENGINES_DIR`
- 컨테이너 안 경로는 **약속된 고정 경로**를 쓴다. 예: `/data`(입력, 읽기 전용) · `/models` · `/results`(출력)
- 버전이 붙는 파일은 파일명에 버전을 넣는다. 예: `model-v1.pt`, `model-v2.pt`

### 1-3. 헬스체크 엔드포인트 (M12-C)
- `/health` 는 "프로세스가 떴다"(1층)가 아니라 **"요청을 처리할 준비가 됐다"(2층, 리소스 로딩 완료)** 일 때만 `200` 을 반환한다.
- 버전 확인용 엔드포인트(예: `/version`)를 둔다. 운영 중 "무엇이 어떤 버전으로 떠 있나"를 확인하는 수단이다. (부록 B 시나리오①)

### 1-4. 로그 (M2-D, M12-C, M5-D)
- 로그는 **파일이 아니라 stdout** 으로 출력한다. 수집·회전은 인프라(Docker)의 일이다.
- 한 줄에 구조화된 정보(예: `request_id`, 버전)를 담는다.
- **비밀값(비밀번호, 토큰, 키)은 로그에 절대 출력하지 않는다.** 에러 덤프에 섞여 나가지 않게 코드에서 주의한다.

### 1-5. 외부 연결 재시도 (M7-B)
- DB 등 외부 연결은 **재시도 후 포기** 로직을 둔다. (예: 5회, 2초 간격 → 그래도 실패하면 명확히 종료)
- 시작 시점은 Compose 의 healthcheck 대기가, 운영 중 끊김은 앱의 재시도가 담당한다 — 두 층을 모두 둔다.

### 1-6. 서버 수신 주소 (M3-B, M5-E)
- 컨테이너 안 서버는 `--host 0.0.0.0` 으로 띄운다. `127.0.0.1` 로 띄우면 컨테이너 밖에서 접속되지 않는다(연결 거부의 대표 원인).
- **[프로젝트 적용]** 기존 `ops/gateway.mjs` 는 web·model-api 를 `127.0.0.1` 로 고정 호출해서, 현재는 `network_mode: service:web` 로 우회 중이다. 재구성 시에는 **호출 대상 주소를 환경변수로 빼고, 서비스 이름(예: `http://model-api:8000`)으로 호출**하도록 바꾸는 것을 목표로 한다. (원칙 5)

## 2. Dockerfile 작성 규칙

### 2-1. 기본 구조와 순서 (M3-B, M3-D)
- 순서: `FROM` → `WORKDIR` → **의존성 파일만 COPY** → 의존성 설치 `RUN` → **앱 코드 COPY** → `USER` → `CMD`
- 이유: 자주 바뀌는 것(코드)을 뒤로, 안정적인 것(의존성)을 앞으로 두어야 빌드 캐시가 재사용된다.
- **[프로젝트 적용]** Python 은 `pyproject.toml` + `uv.lock` 을 먼저 COPY → `uv sync --frozen`, Node 는 `package.json` + `package-lock.json` 을 먼저 COPY → `npm ci`.

### 2-2. 기반 이미지 (M9-E, 치트시트)
- 기본은 **`-slim`** 변종. Alpine 은 musl 기반이라 ML·과학 패키지 호환성 문제가 있어 피한다.
- 태그는 **버전을 명시**한다. `latest` 금지.
- **[프로젝트 적용]** model-api 는 `requires-python >=3.11,<3.13` 이므로 `python:3.11-slim` 계열을 유지한다. (강의 예제의 3.12 를 그대로 따르지 않는다)

### 2-3. 멀티스테이지 빌드 (M3-E)
- 빌드 도구(컴파일러, dev 의존성)는 `builder` 단계에만 두고, 최종 단계에는 실행 산출물만 `COPY --from=builder` 로 옮긴다.

### 2-4. 실행 명령 형식 (M3-C)
- `CMD` · `ENTRYPOINT` 는 **exec(배열) 형식**으로 쓴다. 예: `CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]`
- shell 형식은 PID 1 이 셸이 되어 종료 신호(SIGTERM)가 전달되지 않고, 10초 뒤 강제 종료(SIGKILL)될 수 있다.
- `ARG` 는 빌드 시에만 필요한 값, `ENV` 는 실행 중에도 필요한 값에 쓴다. `EXPOSE` 는 문서일 뿐 실제 공개는 포트 매핑이 한다.

### 2-5. non-root 실행 (M9-B)
- 전용 사용자를 만들고 → 소유권을 넘기고 → `USER` 로 전환한다.
  ```dockerfile
  RUN useradd --uid 1000 appuser && chown -R appuser:appuser /app
  USER appuser
  ```
- 확인: `docker compose exec <서비스> id` 결과가 root 가 아니어야 한다.

### 2-6. .dockerignore (M3-D)
- 모든 Dockerfile 에 `.dockerignore` 를 둔다. 최소 포함: `.git/` · `__pycache__/` · `*.pyc` · `.venv/` · `node_modules/` · `*.log` · **`.env`** · `tests/` · `docs/`
- `.gitignore` 와 짝을 이루는 이중 방어다.

### 2-7. 버전 고정 (M12-B)
- 의존성은 lock 파일 또는 `==` 로 고정해 재현성을 보장한다.

### 2-8. HEALTHCHECK (M12-B)
- 이미지에 `HEALTHCHECK` 를 선언하거나 Compose 의 `healthcheck:` 로 `/health` 를 호출한다. slim 이미지에 `curl` 이 없으면 `python -c "import urllib.request; ..."` 방식을 쓴다.

## 3. 설정값·비밀값 규칙 (M5-D)

| 구분 | 예 | 취급 |
|---|---|---|
| 일반 설정값 | DB 호스트 이름, 포트, 로그 레벨, `APP_MODE` | 파일로 공유 가능 (`.env.example` 에 기본값) |
| 비밀값 | 비밀번호, API 키, 토큰, 개인키 | 실행 시에만 주입. 접근 통제 필요 |

**비밀이 있으면 안 되는 곳 4가지**
1. 이미지 안 (`ENV` 로 굽기, `COPY .env`) — 절대 금지
2. Git 저장소 — `.gitignore` + `.dockerignore` 로 이중 방어
3. 로그·명령 기록
4. 소스 코드 (하드코딩된 키는 발견 즉시 교체)

- 형식 공유는 `.env.example` 로만 한다. 문서·로그에는 **키 이름만** 적는다. (M12-E)
- Docker Hub 로그인은 계정 비밀번호가 아니라 **액세스 토큰**으로 한다. 토큰은 소스·compose 파일·스크립트에 하드코딩하지 않는다. (M8-B)

## 4. Compose 구성 규칙

### 4-1. 공개/내부 분리 (M7-A, M9-C)
- 사용자가 닿는 서비스만 포트를 공개한다. DB 는 호스트 포트를 열지 않고 내부 네트워크에만 둔다.
- 네트워크는 용도별로 나눈다. 예: `frontend`(공개) · `backend`(내부)
- **[프로젝트 적용]** 현재처럼 외부 포트는 `127.0.0.1` 에만 바인딩하는 방식을 유지한다 (9503 서비스 입구, 26101 관리자).

### 4-2. 시작 순서보다 준비 상태 (M7-B)
- `depends_on` 만으로는 "컨테이너 시작 순서"만 보장된다. DB 처럼 초기화가 필요한 서비스는 `healthcheck` 를 정의하고 `condition: service_healthy` 로 기다린다.
  ```yaml
  depends_on:
    db:
      condition: service_healthy
  ```

### 4-3. 이름이 주소 (M5-C, 원칙 5)
- 서비스 간 호출은 IP 가 아니라 **서비스 이름**으로 한다. IP 는 재생성 시 바뀐다.

### 4-4. 환경별 파일 분리 (M7-C)
- 공통(`compose.yaml`) + 개발(`compose.override.yaml`, 자동 병합) + 운영(`compose.prod.yaml`, `-f` 로 명시) 3층 구조.
- 개발: 소스 바인드 마운트, 상세 로그 / 운영: 이미지에 굽기, 고정 태그, `restart: unless-stopped`
- 병합 결과는 반드시 `docker compose ... config` 로 확인한다.
- **[결정 필요]** 강의 표기는 `compose.yaml`, 현재 프로젝트는 `docker-compose.yml`. 재구성 시 파일명 통일 여부를 정한다.

### 4-5. 값의 세 문법 구분 (M7-D)
- `.env` + `${VAR}` = 파일 안 문자 **치환**
- `environment:` = 컨테이너에 환경변수 **주입**
- `env_file:` = 파일 통째 주입

### 4-6. 자원 한도와 보안 옵션 (M9-C, M9-D, 치트시트)
- `mem_limit` 등 자원 한도는 **측정한 최대 사용량 + 여유분**으로 정한다 (`docker stats` 근거). 감으로 정하지 않는다.
- 적용 검토 항목: `user` (non-root) · `read_only: true` + 쓰기 필요한 경로만 볼륨/tmpfs · `cap_drop: [ALL]` 후 필요한 것만 추가
- **금지**: `privileged: true` · Docker 소켓(`/var/run/docker.sock`) 마운트 · 호스트 루트 통째 마운트(`/:/host`)
- 읽기만 하는 마운트(모델, 음원, 입력 데이터)는 `:ro` 를 붙인다. (M10-D)

### 4-7. 데이터 보존 (M4, 치트시트)
- DB·업로드 등 사라지면 안 되는 데이터는 **이름 있는 볼륨**에 둔다.
- `docker compose down -v` 는 볼륨까지 지우므로 쓰지 않는다. `prune` 전에는 무엇이 지워질지 먼저 확인한다. (M8-E)

## 5. 이미지 태그·배포·롤백 규칙 (M8)

### 5-1. 이미지 이름
- Docker Hub 형식: `<사용자명>/<이미지명>:<태그>` (예: `hong/myapi:1.2`)

### 5-2. 태그 전략 (M8-C)

| 종류 | 예 | 규칙 |
|---|---|---|
| 릴리스 버전 | `1.0`, `1.2` | **한 번 push 한 릴리스 태그는 다시 push 하지 않는다** |
| Git 연결 | `1.2-g5f4e3d` | 이미지와 커밋을 연결 — 배포 추적용 |
| 환경별 | `dev`, `staging` | 의도적으로 이동하는 포인터 |
| `latest` | — | **운영 배포에 쓰지 않는다** (재현 불가) |

- 정확한 고정·롤백·감사 기록에는 태그가 아니라 **digest(`sha256:...`)** 를 쓴다. push 후 출력되는 digest 를 기록한다.

### 5-3. 배포 흐름 (M8-D)
`코드 변경·커밋 → 빌드 → 이미지 점검(크기·취약점) → tag·push(digest 기록) → 받은 곳에서 실행 검증 → 기록`
- 취약점 점검: `docker scout cves <이미지>` — 발견 시 기반 이미지·의존성 갱신 후 **새 이미지로 교체**한다.
- 배포 완료의 기준은 `up` 이 아니라 **받은 곳에서의 정상 응답**이다. (M8-E)

### 5-4. 아키텍처 확인 (M8-E)
- `exec format error` 는 이미지와 기계의 CPU 아키텍처 불일치다. `docker image inspect` 로 Architecture 를 확인한다.
- **[프로젝트 적용]** 기존 코드는 macOS arm64 에서, 현재 작업 PC 는 Windows x64(amd64). 팀원 간 이미지를 공유할 때는 아키텍처를 확인하고, 필요하면 멀티 아키텍처 빌드를 쓴다.

### 5-5. 롤백 (M12-D, 원칙 9)
- 이전 버전 태그를 지우지 않는다. 문제 시 compose 의 이미지 태그를 이전 버전으로 바꾸고 `docker compose pull && docker compose up -d`.

## 6. 검증 규칙 (M12-D, M7-E)

### 6-1. 입력 케이스 시험

| 케이스 | 기대 응답 |
|---|---|
| 정상 입력 | `200` + 결과 + 버전 |
| 필수 필드 누락 | `422` |
| 잘못된 자료형 | `422` |
| 리소스 로딩 실패 상태 | `500` + 메시지 |

### 6-2. 장애 재현 3종
1. 리소스 파일 누락 (잘못된 경로) → 로그에 `FileNotFoundError` → 설정 수정 후 재생성
2. 잘못된 환경설정 (포트·모드 불일치) → `config → ps → logs → exec` 순서로 점검
3. 메모리 부족 → `Exited (137)` + `OOMKilled: true` → 측정 근거로 한도 조정

### 6-3. 연결 오류 구분 (M5-E)

| 증상 | 의미 | 먼저 볼 것 |
|---|---|---|
| `Name or service not known` | 이름 해석 실패 | 같은 네트워크인가 |
| `Connection refused` | 도달했지만 수신 프로세스 없음 | 포트 매핑·수신 주소(0.0.0.0)·실행 상태 |
| `address already in use` | 호스트 포트 충돌 | `docker ps` 의 PORTS |

### 6-4. 진단 순서
`docker compose config`(설정) → `ps`(상태·헬스) → `logs -f <서비스>`(로그) → `exec <서비스> sh`(내부)

## 7. 문서화 규칙 (M12-E, 부록 B)

- 서비스마다 **Runbook** 을 남긴다. 최소 목차:
  - **무엇** — 이미지(digest 까지)·모델 버전·포트·환경변수 키 이름·아키텍처
  - **어떻게** — 기동·확인(`/health`, `/version`)·점검·정지
  - **만약에** — 장애별 `증상 → 근거 → 조치` + 롤백 절차
- 장애 보고는 4줄: 증상 / 근거(로그·종료코드 원문) / 영향 / 조치
- 문서와 제출 자료에 비밀값·실데이터가 없는지 점검한다.
- 검증 기준: 다른 사람이 **문서만 보고** 재현할 수 있어야 한다.

---

## 8. 커밋 규칙

- 커밋 메시지는 Conventional Commits 규칙을 따른다. (사용자 작업 지시)
  - 예: `feat(model-api): add /version endpoint` · `build(docker): pin python 3.11-slim base` · `fix(gateway): call services by name instead of 127.0.0.1` · `docs: add API rework rules`
- 이미지 릴리스 태그와 Git 커밋을 연결한다 (`<버전>-g<짧은 커밋 해시>`). (M8-C)
