## 7. 작업 규칙

1. **이슈 → 브랜치 → PR → 리뷰 → 병합.** 브랜치 이름은 `<type>/<이슈번호>-<짧은 설명>` (예: `feat/12-auth-session`), PR 본문에 `Closes #12`.
   - **push 전에 항상 pull 한다** (2026-10-30 추가 — 여러 사람이 수시로 `main` 에 병합한다)
     ```bash
     # 작업 시작 전 — 최신 main 에서 브랜치를 딴다
     git switch main
     git pull
     git switch -c feat/12-auth-session

     # push 전 — 원격 main 이 앞서 있으면 내 브랜치에 합친다
     git fetch
     git merge origin/main        # 아직 한 번도 push 안 한 브랜치면 git rebase origin/main 도 된다
     # 충돌이 나면 고치고 → 빌드 · 시험 확인 → git add · git commit
     git push                     # 처음이면 git push -u origin feat/12-auth-session
     ```
   - 이미 push 한 브랜치는 rebase 하지 않는다. **강제 push(`--force`) 금지**, 특히 `main`.
   - PR 을 병합하기 전에도 GitHub 에서 "This branch is out-of-date" 가 보이면 먼저 `main` 을 합친다.
2. **GitHub 에 남기는 글은 한글로 쓴다** (2026-10-30 추가) — 커밋 메시지 · PR 제목 · PR / 이슈 본문 · 리뷰 댓글.
   - 커밋 메시지 형식은 Conventional Commits. **앞의 종류 · 범위만 영어, 설명은 한글**: `feat(backend): 로그인할 때 세션을 새로 발급` · `build(model-api): 기반 이미지를 python 3.11-slim 으로 고정` · `docs(contracts): web-api 계약에 화면 대조 결과 반영`
   - 종류: `feat` 기능 · `fix` 버그 수정 · `docs` 문서 · `build` 빌드 · Docker · `test` 시험 · `chore` 그 밖 · `refactor` 동작은 같고 구조만 바꿈
   - 브랜치 이름 · 파일 이름 · 코드 안의 이름은 영어로 둔다 (도구 호환).
3. 같은 파일을 함께 고치지 않는다:
   - 서비스 정의는 각 서비스 폴더의 `compose.yaml` (루트는 `include` 만)
   - 서비스마다 lock 파일 따로 · score-core 는 `file:` 경로로 연결
   - DB 마이그레이션은 `YYYYMMDD_HHMM_<설명>.sql` 로 **새 파일만 추가**
   - 오류 코드는 `shared/errors/{common,web,model}.json` 영역별 파일
4. 계약(`api/contracts/`)을 바꾸려면 `contract` 라벨 PR → 상대 담당 리뷰 → 병합 후 구현.
5. 코드 작성 규칙은 [API_재구성_작성규칙.md](API_재구성_작성규칙.md) 를 따른다 (`0.0.0.0` 수신 · 서비스 이름으로 호출 · `/health` 는 준비 완료 기준 · 로그는 stdout · non-root · `latest` 미사용).
6. 비밀값(`.env` · 키 · 토큰 · Tailscale 인증 키)은 저장소 · 이미지 · 로그 · 이슈에 넣지 않는다. 형식은 `.env.example` 로만 공유한다.
7. 막히면 `blocked` 라벨과 원인 · 필요한 도움을 이슈에 적는다. 결정 사항은 채팅에만 남기지 말고 이슈에 기록한다.

## 8. Limit day 시험 · 자원 측정 기록 (2026-11-04, #49 일부)

서버 PC 에서 서버와 **같은 이미지**로 띄운 임시 프로젝트(DB · 볼륨도 임시)로 시험했다. 실제 서비스의 DB · 볼륨은 건드리지 않았다. 자세한 기록은 팀장 PC 의 로컬 문서(`docs/시험기록_20261104_시계교정후_기능시험.md`)에 있다.

### 8-1. 서버 시계 교정

- 증상: 컨테이너 시계가 약 5초마다 15초씩 뒤로 갔다 돌아왔다 → 시간 초과 · 마감 계산이 흔들렸다(#105 원인).
- 원인: Windows 호스트 시계가 외부 시각보다 **15.1초 빨랐고**(`w32time` 정지), WSL2 안의 두 시간 동기화 주체가 서로 맞추려 싸웠다.
- 조치: 호스트 `w32time` 을 자동 시작으로 켜고 시간 서버를 `time.cloudflare.com` 으로 바꿔 맞췄다. 변경 전 · 후 값과 되돌리는 방법은 `PC_설정_변경기록.md`.
- 결과: 교정 뒤 15초 왕복 **0회**. 서버 컨테이너 시각과 호스트 시각이 같다.

### 8-2. 기능 시험

- 시험 범위: 가입 · 로그인 · 예시 · 올리기 · 인식(오선보 · 정간보) · 편집 · 내려받기 4형식(MusicXML · MIDI · PDF · MP3) · 공유 · 외부 API · 음원 라이선스 · 주기 정리 · demo · 백업.
- 결과: **제품 결함 0건.** 시험 도구의 기대가 틀려 실패로 적힌 10건은 설계된 동작임을 확인하고 올바른 기대로 다시 통과시켰다(예: 사용자 업로드는 사진 · PDF 만 받는다).
- 이미 알려진 것: 외부 키 결과의 파일 주소에 포트가 빠진다(#154).
