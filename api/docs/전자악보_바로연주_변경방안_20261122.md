# 변경방안: 전자 악보(MusicXML · MIDI)로 바로 연주하기

> 2026-11-22 · 검토 요청 문서 (구현 전)
> jsg 의 지시로 Claude 가 코드 · 문서를 읽어 검토하고 이 문서를 작성했다. 「확인」은 코드 · 문서로 본 것이고, 「추정」은 실행해 보지 않고 판단한 것이다.
> 이 PR 은 문서만 더한다. 코드는 바꾸지 않는다. 합의되면 구현 이슈를 따로 만든다.
> 2026-11-26 리뷰 반영: jsg 의 지시로 Claude 가 PR #199 리뷰(피클 11-22 1~10번 · 황송해 11-23 · 예은 11-25 4건과 피클의 대조 11-25)를 main 코드와 다시 대조하고 이 문서에 넣었다. 무엇을 어디에 넣었는지는 11절.

## 1. 배경 — 왜 바꾸려 하나

- 지금은 사진 · PDF 로 악보를 올리고 **인식(OMR)을 거쳐야만** 연주를 들을 수 있다.
- MusicXML · MIDI 처럼 이미 전자 악보를 가진 사용자도 연주를 들으려면 악보를 이미지로 바꿔 인식에 맡겨야 한다. 인식 시간이 걸리고, 인식 오류로 원래보다 나쁜 악보가 될 수도 있다.
- **제안:** 연주 부분이 인식과 따로 동작하게 해서, 전자 악보를 넣으면 **바로 국악기로 바꿔 들어 볼 수 있는 길**을 지금 기능 옆에 추가한다. 첫 안내에서 「전자 악보 바로 듣기」를 따로 보여 준다.

## 2. 결정 (팀 검토 결과)

1. **2026-09-29 「직행 없음」 결정을 바꾼다.**
   - 당시 이유: 인식에 집중하기 위해서였다. 프로젝트 주제가 국악보 인식 · 변환이라 인식을 거치지 않는 길(UC4 직행)을 범위에서 뺐고, 기술적으로 막힌 것은 없었다(황송해 답, 11-23).
   - 기록: tag \`v0.1.1\` \`proto_type/src/app/docs/reference/UC_00_개요_관리_및_환경_분석.md\` 변경 이력 11행 「연주 API의 MIDI · MusicXML 직행은 유지(현재 기본안, 사용자 확인 대기)」 → 12행 「MIDI · MusicXML은 어디서도 받지 않아 UC4(직행)를 웹·API 모두에서 제거」, 363행 미해결 22 「MusicXML 입력 → 인식 없이 직행, 악보 구조 검사」. 같은 날 「사진 · PDF 입력」 범위 축소와 함께 온 결정이고, 이유는 적혀 있지 않았다.
   - 이번 변경은 인식 경로를 그대로 두고 옆에 길을 하나 더하는 것이라 당시 이유와 부딪히지 않는다(황송해 동의). 구현 때 \`upload-rules.json\` \`$comment\` 에 당시 이유와 이번 변경을 한 줄씩 남긴다(\`docs/API_진행계획.md\` 「결정 사항은 이슈에 기록」).
2. **범위: A(웹 직행) + B-1(외부 API 안내)부터.** B-2 는 수요가 생길 때, C 는 하지 않는다(황송해 · 예은 동의).
3. **첫 단계 형식: MusicXML(\`.musicxml\` · \`.xml\` · \`.mxl\`), MIDI 는 나중(A-3).** 악보 프로그램의 기본 내보내기가 \`.mxl\` 인 경우가 많아 첫 단계에 넣는다(황송해). 그래서 \`.mxl\` 안전 검사가 첫 단계의 선행 작업이다(6절 5번 · 8절 0번).

## 6. 위험 · 쟁점

1. **결정 변경:** 2절 1번에서 합의했다.
2. **프로젝트 주제와 평가:** 주제가 「국악보 변환 · 편집」이라, 인식을 거치지 않는 길이 어떻게 보일지 검토가 필요하다. 「인식이 어려운 악보 · 사용자도 바로 쓸 수 있다」는 장점으로 설명할 수도 있다. 지표는 5절 DB 행처럼 섞이지 않는다.
3. **MIDI 품질:** 사람이 연주해 녹음한 MIDI(박자가 맞춰지지 않은 MIDI)는 악보로 바꾸면 음표가 잘게 쪼개지거나 박자가 어긋날 수 있다(추정) → MIDI 는 A-3 으로 미룬다(2절 3번).
4. **정간보:** 전자 악보는 사실상 오선보 형식뿐이다. 정간보는 계속 사진 · PDF 경로를 쓴다.
5. **안전 검사(\`.mxl\`):** model-api 는 \`_read_mxl()\` 에서 항목 100개 · 해제 합계 20MB 상한을 둔다. 웹은 구조 검사를 옮기지 않았고, score-core \`unpackMusicXml()\` 은 #213(11-26 병합)으로 같은 상한을 갖게 됐다. 남은 일은 웹 검사에 MusicXML 구조 검사(\`UPLOAD_MUSICXML_UNREADABLE\`)를 옮기고, 상한을 넘는 \`.mxl\` 이 반려되는지 시험하는 것이다.
6. **한도:** G12 는 인식 한도가 아니라 **웹 접수 한도**다(\`web/webLimit.ts\` — 계정 · 주소별 처리 중 요청 + 시간당 접수). \`v_web_request_limit\` 은 route 를 가리지 않고 web 요청을 세므로, \`POST /api/requests\` 로 받으면 G12(계약 \`web-api.yaml\` 「처리 중 1건 · 시간당 상한 → 429」)가 그대로 걸린다. \`shared.ts\` 의 「웹 한도는 걸지 않는다」는 [이 악보로 작업하기] 가 \`enforceWebLimit\` 을 부르지 않기 때문이지 직행이라서가 아니다. 직행도 한도를 걸지(제안: 건다 — 접수 남용을 막는 장치라 경로와 관계없다), 건너뛸지 구현 이슈에서 정해 계약에 적는다. MP3 내려받기는 \`/v1/render/mp3\` 를 써서 렌더 한도가 그대로 걸린다.
7. **음원 라이선스 · B-1 응답:** 외부 API MP3 는 \`v_mp3_license\` 가 확인되기 전까지, 또 서비스 키가 아니면 \`render.py\` 가 200 JSON(\`mp3_withheld\` · \`mp3_withheld_reason\` · \`message\`)을 돌려준다(확인). B-1 안내의 호출 예시에 \`audio/mpeg\` · JSON 두 응답과 라이선스 제한을 함께 적는다.
8. **재생 지연(B3):** 브라우저 첫 재생 때 sf2 를 약 170MB(\`gugak.sf2\` 22MB + \`FluidR3_GM.sf2\` 148MB) 받는 문제는 이 경로에도 남는다. 「바로 듣기」를 내세우려면 B3 개선을 같이 보는 것이 좋다.
9. **MusicXML 연주 품질(P1, 예은):** score-core 는 꾸밈음(\`<grace>\`)을 건너뛰고(길이가 없어서), 템포는 첫 값 하나만 \`doc.tempoBpm\` 으로 남기며, 반복기호(\`<repeat>\` · 볼타)는 읽지 않는다(확인, 피클 대조). 지원하는 음악 요소 범위를 문서 · 안내에 적고 완료 기준(8절)에서 시험한다.
10. **성부 번호(P2, 예은):** \`completeDirect()\` 는 악기 이름이 있는 성부만 고른 뒤 \`i + 1\` 을 \`part_no\` 로 쓴다. 가운데 성부에 악기 이름이 없으면 뒤 성부 번호가 당겨진다(3성부 가운데가 비면 3번이 2번으로 저장). \`doc.parts\` 의 실제 위치로 저장하고 그런 악보를 시험에 넣는다.
11. **직행 실패 처리(P2, 예은):** \`completeDirect()\` 는 DB 트랜잭션 전에 \`result.musicxml\` · \`result.mid\` 를 저장한다. 그 뒤 DB 가 실패하면 파일만 남고 요청은 진행 중으로 남는다. 정리 · 재시도 규칙을 구현 이슈에서 정한다.

| 사진 · PDF 악보 변환 | PNG · JPG · WEBP · PDF + 오선보/정간보 | 인식 → 결과 판별 → 편집 · 연주 | 「종이 악보를 찍거나 PDF 로 올리면 악보로 바꿔 드려요」 |
| **전자 악보 바로 듣기** | MusicXML(.musicxml · .xml · .mxl). MIDI 는 A-3 에서 | 바로 연주 · 악기 바꾸기 | 「MusicXML 파일이 있으면 인식 없이 바로 국악기로 들어 볼 수 있어요」 |

전자 악보 카드에서는 오선보/정간보 선택을 숨기고, 악보 종류가 없으면 [다음]을 막는 조건을 함께 푼다(황송해 담당).

## 8. 진행 순서

0. 선행: \`.mxl\` 압축 해제 상한 — score-core 는 #212 · PR #213 으로 끝남(11-26). 웹 검사의 구조 검사 이전은 A-1 에서 한다.
1. 구현 이슈 작성. 선행 공용 파일: \`api/shared/upload-rules.json\` · \`api/shared/fixtures/upload/expected.json\` · \`api/contracts/web-api.yaml\`. DB 스키마는 바꾸지 않는다(5절 DB 행).
2. A-1: MusicXML(\`.musicxml\` · \`.xml\` · \`.mxl\`) 웹 직행(저장 → \`completeDirect()\` → 첫 악기 기록), 웹 구조 검사, G12 결정, 시험 갱신.
3. A-2: 첫 화면 두 갈래 안내(황송해).
4. B-1: API 안내에서 \`render/mp3\` 를 「전자 악보 연주」로 소개(두 응답 형식 포함).
5. (선택) A-3 MIDI, B-2 \`/v1/performances\` 직행(\`origin='direct'\` 포함), B3 재생 지연 개선.

**완료 기준 (구현 이슈에서 확인할 것)**
- MusicXML(\`.mxl\` 포함)을 올리면 인식 작업 없이 \`route=direct\` 로 완료되고, 원본이 \`upload_file\` 로 남고, 첫 악기가 기록되며, 연주 화면에서 악기를 바꿔 재생된다.
- 사진 · PDF 경로와 \`/v1/omr/*\` · \`/v1/performances\` 의 반려 규칙은 바뀌지 않는다(창구별 공유 기대값으로 확인).
- 깨진 MusicXML 은 422 \`UPLOAD_MUSICXML_UNREADABLE\` 로, 상한(항목 100개 · 해제 20MB)을 넘는 \`.mxl\` 은 반려된다.
- 지원 요소 범위를 적고 시험한다: 음높이 · 음표 길이 · 박자 · 화음 · 여러 성부 · 붙임줄 · 반복기호 · 꾸밈음 · 템포 변화 · 국악기로 바꿀 때 음역 · 타악기. 지원하지 않는 요소는 안내에 적는다.
- 가운데 성부에 악기 이름이 없는 악보에서도 \`part_no\` 가 원래 위치와 같다.
- 결과 파일 저장 뒤 DB 가 실패하는 경우의 요청 상태 · 남은 파일 처리가 정한 규칙대로다.
- G12 적용 여부가 계약과 같다.
