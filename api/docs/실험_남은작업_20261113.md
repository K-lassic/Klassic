## 2. 먼저 — 서비스 다시 켜기 (A 항목의 공통 준비)

실험을 마친 PC 는 서비스를 `docker compose stop` 으로 멈춘 상태다. 컨테이너 · 볼륨 · 이미지는 그대로 있다. `down -v` 는 쓰지 않는다.

- **조건**: 같은 PC 의 `api/` 폴더, `.env` 가 있다 (값은 Git 에 없다). 엔진 볼륨 `klassic_engines_home` 이 있다.
- **절차** (Git Bash, `api/` 폴더):
  1. `docker volume ls` — `klassic_engines_home` 과 `klassic-api_*` 볼륨이 있는지 확인한다.
  2. `docker compose up -d --wait` — 이미지가 있으므로 빌드 없이 뜬다.
  3. `docker compose ps` — `db` · `web` · `admin` · `frontend` · `model-api` 가 healthy, `migrate` · `shared-storage-init` 은 `Exited (0)`.
- **서비스 키**: 이 PC 의 `.env` 에 이미 들어 있다. 볼륨을 새로 만들었다면 구축방법 6절로 운영자 · 서비스 키를 다시 발급하고 `web` 을 다시 만든다 (`docker compose up -d web`).
- **성공 기준**: `http://127.0.0.1:9603/api/health` 와 `/api/v1/health` 가 200. `pwsh deploy/check-public.ps1 -Url http://127.0.0.1:9603 -Local` 이 「모두 통과」.
- **주의**: 같은 계정을 새 세션으로 다시 로그인하면 10분 동안 `LOGIN_ALREADY_ACTIVE` 다. 시험 계정은 새로 가입해서 쓴다. 로그인 세션은 약 7시간 뒤 만료된다.

## 3. A · B — 실험 항목

### A. 서비스 키가 필요한 항목

#### E-4. 재빌드 전후 인식 결과 비교
- **조건**: 같은 커밋(같은 `main`)에서 빌드한 두 판본. 한쪽은 `before` 태그로 남긴 이미지.
- **절차**: 이미지 3개(`backend:dev` · `frontend:dev` · `model-api:0.2.2`)를 `before-<날짜>` 태그로 남긴다 → `docker compose build --no-cache` 로 다시 빌드 → 같은 예시 3개(아리랑 세마치 · 미뉴에트 · 타령)를 각 판본으로 인식한다.
- **성공 기준**: `route=recognize` · `fallback=false`, 결과 악보의 구조가 같다 (마디 수 · 음표 수 · 음높이 순서). 바이트 해시는 기준으로 쓰지 않는다 (정간보 PDF 는 파트 ID 가 바뀐다).
- **기록**: 이미지 ID 가 같은지 (재현성의 정의를 여기서 정한다).

#### E-7. 이전 이미지 태그로 실제 롤백
- **조건**: E-4 에서 남긴 `before-*` 태그.
- **절차**: `MODEL_API_IMAGE` 를 이전 태그로 지정해 `docker compose up -d --no-deps --wait model-api` → `/api/v1/health` → 예시 1개 인식.
- **성공 기준**: 되돌린 뒤 health 200, 인식이 같은 결과. 걸린 시간을 적는다 (회사 PC 기준 대역 복귀 14~21초, 이전 태그 롤백은 미측정).

#### E-8. 대역 전환과 복귀 시간
- **조건**: 대역 이미지 `klassic/klassic-model-api:0.1.1` 이 필요하다 (이번 정리에서 삭제했다 → 다시 만들거나 받아야 한다). `SERVICE_API_KEY` 필요.
- **절차**: 구축 Runbook 의 대역 전환 명령 → `model-api` 가 Healthy 가 되기까지 시간 측정 → 재구성판으로 복귀.
- **성공 기준**: 전환 후 로컬 공개 점검 통과, 복귀 후 `route=recognize`.

#### E-11 (동시). 동시 인식 때 자원
- **절차**: 예시를 동시에 여러 건 올리면서 `docker exec <컨테이너> cat /sys/fs/cgroup/memory.peak` 로 최대 메모리를 읽는다. **`docker stats --no-stream` 을 반복 루프에 넣지 않는다** (자동화에서 멈춘다).
- **성공 기준**: `web`(한도 1GiB) · `model-api`(한도 4GiB) 가 한도를 넘지 않는다. 접수 자리는 실행 1 + 대기 1 이라 3번째 요청은 `SERVER_BUSY` 일 수 있다 (설계된 동작).
- **참고 값**: 이 PC 순차 6건 `model-api` 최대 2,967MiB, 회사 PC 동시 6건 렌더링 3.35GiB.

#### 브라우저 전체 흐름 (구축방법 8절)
- 가입 → 로그인 → 예시 선택 → 인식 결과 → 내려받기, 화면 · 소리. 이번 실험은 API 로만 했다.

### B. 서비스 키가 필요 없는 항목

#### E-10. 사운드폰트가 없을 때 동작
- **조건**: 별도 복사본(예: 임시 폴더에 `GIT_LFS_SKIP_SMUDGE=1 git clone`). 실제 작업 폴더의 사운드폰트를 바꾸지 않는다.
- **절차**: 포인터 파일만 있는 상태로 `up` 한다.
- **성공 기준**: 실패가 조용히 넘어가지 않고 사용자나 운영자가 원인을 알 수 있는 메시지가 나온다. 나오지 않으면 구축방법 10절에 증상을 추가한다.

#### E-5. 처음 접속 지연 재현과 개선 확인
- **조건**: `fix/first-visit-sound-preload` 의 변경(`S1Upload.vue`)을 서버 노트북의 stash 에서 가져와야 한다 (이 PC 에는 없다). `vue-tsc` 와 `vitest` 를 먼저 돌린다.
- **절차**: 브라우저 네트워크 제한(느린 3G 등)에서 변경 없이 → 변경 적용 후, 로그인 → 올리기 → 인식 대기 → 결과 → 첫 소리까지 구간별로 잰다.
- **성공 기준**: 음원 요청이 인식 대기 중에 나가고, 첫 소리까지 시간이 줄었다.

#### E-2. 운영자 명령의 `-it`
- **사용자가 직접** Git Bash · PowerShell 7 에서 `docker compose run --rm -it web node dist/tools/createOperator.js --login <아이디> --name <이름>` 을 실행한다 (Claude 환경에는 TTY 가 없어서 확인하지 못했다).
- **성공 기준**: 비밀번호를 두 번 묻고 계정이 만들어진다. 실패하면 `winpty` 를 붙여 결과를 적고, 구축방법 6절의 대안이 맞는지 확인한다.

## 5. D — 문서 고치기 (PR #183 에 반영)

실험결과 4절의 4건을 구축방법 문서에 반영한다.

1. 2절 — `FluidR3_GM.sf2` 를 `curl` 로 받는다는 설명과 실제(LFS 로 내려옴)를 맞춘다.
2. `.env.example` — `ENGINES_VOLUME_NAME` 키를 추가한다.
3. 5절 — 「새 볼륨이면 서비스 키를 먼저 발급해야 `web` 이 뜬다」는 문구를 바로잡는다 (키 없이도 healthy).
4. 10절 — 키가 없을 때의 증상을 「접수(202) 뒤 대체 악보 · `ENGINE_DOWN`」으로 고친다. 백엔드가 model-api 의 401 을 `ENGINE_DOWN` 으로 바꾸는 경로는 코드로 아직 확인하지 않았다 (추정).

## 6. 정리 · 보관 (실험을 모두 끝낸 뒤)

- 롤백용 `before-*` 태그와 대역 이미지는 E-7 · E-8 이 끝난 뒤 지운다 (지우기 전에 이름과 용도를 확인).
- 시험용 계정(운영자 `exp-op` · 일반 시험 계정)은 DB 와 함께 볼륨에 있다. 서비스용으로 쓸 PC 라면 볼륨을 새로 만든다. 지우기 전에 대상을 확인한다.
- 실험 전에 만든 백업(로컬 폴더, tar 6개)은 실험이 끝나고 필요 없다고 확인한 뒤에 지운다. GitHub 에는 올리지 않는다.
